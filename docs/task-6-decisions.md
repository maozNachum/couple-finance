Use **A: immutable financial transaction revisions** for categorization. The existing complete-history readers, ledger, atomic audit, account locking and expected-version protocol already understand this envelope. Category-only revisions preserve transaction/allocation IDs and every financial field, so they replace the previous version without changing its balance contribution. The tradeoff is more full revisions and conservative conflicts between financial and category edits. Old revisions are never rewritten. This is simpler and less error-prone than overlays with a second correction/concurrency lineage.

Contract extensions: versioned household Category and Rule records, catalog generation, explicit definition commands, single-allocation categorization commands, and a portable deterministic preview. Existing allocation metadata remains canonical. Stored revision validation accepts authorized USER/RULE categories; manual financial commands may only preserve prior category metadata, while new allocations remain uncategorized. SQL independently enforces this distinction. Add household/category composite FKs before enabling category IDs. Keep prior merged migrations intact. Exact aliases are extended together in policy, TypeScript and Deno.

Categories have immutable identity, household and EXPENSE/INCOME kind, Hebrew-capable names and ACTIVE/ARCHIVED status. No hierarchy is justified. Rename/archive are versioned and retain snapshots; archived IDs remain valid historical references but cannot be newly assigned. Category names never change financial effects.

Rules match only the existing description and explicit EXPENSE/INCOME effect. Normalization v1 translates ASCII A–Z to a–z, collapses ASCII space/tab/CR/LF runs to one space and trims those spaces. All other code points, punctuation and Hebrew marks remain exact; no locale dependence, regex input, Unicode guessing or amount-sign inference. Operators: literal CONTAINS and EQUALS. Smaller nonnegative priority wins. At best priority, different target categories are AMBIGUOUS; identical targets choose the lexically lowest normalized UUID and expose the tied rule IDs. Disabled/archived rules and archived categories do not participate. Rule versions retain exact conditions and algorithm version.

Only active-account, non-voided MOVEMENT EXPENSE/INCOME allocations may be categorized. Existing userLocked metadata blocks automatic assignment. Explicit assignment locks USER/true. Clearing removes the category and restores UNCLASSIFIED/false; explicit unlocking preserves the current category and origin and makes it eligible for future explicit application. No bulk legacy unlock or background write. Unknown financial effect stays UNCLASSIFIED and ineligible.

Each application is a bounded batch of one allocation: atomic success or no change, no partial success. Clients submit the preview's catalog generation and transaction revision/version. The server locks household catalog before account, rechecks live authorization, catalog generation, category eligibility and rule selection, then persists one immutable revision and evidence atomically. Retries use durable payload-hash receipts and recheck authorization before returning prior success. Definition edits increment catalog generation, conservatively invalidating all household previews. Creating/editing a rule never reclassifies history. Financial edits preserve category metadata on retained allocation IDs; removing a categorized allocation requires clearing it first.

No dependencies, production deployment, ingestion, AI, taxonomy infrastructure or unrelated refactors are planned.
