# Task 4 decisions

Baseline: master `58fae2360e01f108d305d6709f3dbd99ade6d30b`; post-merge push CI [37813863610](https://github.com/maozNachum/couple-finance/actions/runs/37813863610) passed before implementation. Branch: `feature/task-4-accounts-balances`.

- Accounts retain the canonical Task 2 identity, types, ownership, currencies and policy. Identity, currencies and balance policy cannot be rewritten after creation. Names can be corrected and accounts archived with version checks. Ownership references durable household members; it does not restrict shared visibility.
- Task 5 owns opening/correction entries and posted movements. LEDGER accounts can be created now, but their balance is explicitly unavailable until that ledger exists. No zero balance is inferred and observations cannot supply a ledger balance. CASH requires LEDGER.
- `finance.account_sources` owns source identity/mode independently of account persistence. Creation atomically establishes one MANUAL source; additional FILE_IMPORT/LIVE_SYNC identities can refer to the same account without provider configuration. Household/account/source composite references protect observations. Root uniqueness and correction lineage include source identity.
- Authority is a dated activation: choose the source with the latest non-null `authoritative_from` on or before the requested date. Activation dates cannot tie or be rewritten. Only that source's observations measured at/after its activation and at/before the requested date are eligible. Missing authoritative observations remain missing; no fallback to an older source. The manual baseline starts at `0001-01-01`. Current clients cannot appoint additional sources or change authority. See [review fixes](task-4-review-fixes.md) for the future cutover boundary and limitations.
- Historical FX evidence is reusable across observations/accounts within a household. `finance.fx_evidence` binds a rate ID to an immutable canonical snapshot; an observation ID identifies a measurement, not a rate. The observation retains its original snapshot and source-independent rate provenance. Conversion uses Task 2 `convertMoney` with eight-place HALF_UP rounding and is explicitly labelled historical in the UI. Reporting-date FX selection is a separate future application responsibility, never inferred from this historical conversion. No live FX or reporting totals.
- Curated invoker RPCs and read views retain the Task 3 live-session/member checks. RLS, composite references, immutable history, raw precision checks, per-account write serialization and atomic audit entries protect persistence. No provider adapters, external connections, ingestion or financial execution.
- No new runtime dependencies or server framework. SQL commands own atomic persistence/authorization; pure financial calculations remain solely in core/domain. Browser data access stays inside the accounts feature. No unused application service abstraction is introduced.
