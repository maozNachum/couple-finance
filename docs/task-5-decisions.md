# Task 5 decisions (approved scope implementation)

Baseline: master 266e9caf636180944c2315aac46c232c8d4bd962; PR #2 merged; exact post-merge push CI 37918229576 succeeded. Branch: feature/task-5-transactions-ledger.

Contract review before code: retain canonical Transaction/Allocation/Money/Date/Ownership/SourceIdentity and SafeError unchanged. Add a manual command and persisted revision envelope in contracts/ledger, plus one pure domain/money/ledger module with exact reviewed aliases. Manual scope excludes merchant/category IDs and rule/source categorization until their persistence exists; every allocation retains explicit meaning and durable ownership. No category-name/sign inference.

A stable transaction ID identifies one movement. Immutable revisions have separate UUIDs, sequential versions and a predecessor revision ID; each contains the complete canonical transaction and allocations. Changes require the latest expected version, predecessor and a nonblank reason. Financial date, source, opening role and stable identity cannot be changed; ordinary movements can be voided and recreated to correct their date. Opening dates are fixed anchors. PENDING may become POSTED or VOIDED; POSTED may be corrected or VOIDED but cannot become PENDING; VOIDED ordinary movements are terminal. A voided opening can be restored to POSTED through an explicit reasoned revision, with the same identity/date and concurrency checks. Views use currently corrected knowledge, not recorded-time snapshots. Retained revisions explain prior states. No automatic opposite-account entry or matching.

Exactly one opening movement per LEDGER account, at start of its financial date. Opening allocations are ADJUSTMENT and its explicit COMPLETE/PARTIAL coverage states whether the starting balance is known. A voided/missing opening or cutoff before it yields UNKNOWN, not zero. Complete opening of zero yields known zero. Partial opening yields INCOMPLETE with an explicitly partial amount. Posted movements on/after opening through the inclusive cutoff contribute; pending/voided do not. Entries may arrive out of date order within that range. Reject any entry before an existing opening; reject an opening later than any existing movement. Opening date is immutable; its amount/coverage may be corrected. Archived history is readable, new commands rejected; previously successful exact retries still succeed for authorized callers. Ledger reports account currency only; no invented reporting FX. OBSERVED behavior is unchanged.

Command receipts scope keys to household/account/manual source. SHA-256 of the complete JSONB command excluding the key is computed in PostgreSQL; object key ordering is irrelevant, array ordering and raw string representations matter. Exact committed replay returns original revision/version; different payload with the same key returns CONFLICT. All validation/history/allocations/receipt/audit writes are atomic. Failure stores no receipt. Per-account row locks serialize commands with archival; version/predecessor checks reject competing changes. Receipt lookup precedes version/archive checks but follows live authorization. Different keys with the same identity conflict. UI retains the same immutable command on uncertain delivery and prevents concurrent submission; no offline persistence.

Invoker API wrapper delegates to a narrow private fixed-search-path definer command because clients must have no direct INSERT/UPDATE/DELETE privileges on financial revisions, allocations or receipts. The private command independently enforces database membership/session checks and context predicates, including direct invocation. Reads are invoker views/snapshot with RLS. No client-supplied actor/timestamps, no user_metadata authorization. Atomic private audit stores only actor/context/revision/operation, no amounts/descriptions. Restrictive composite FKs retain account/source/member identity.

Pure calculation validates complete revision lineage, context and opening policy before summing through the existing decimal wrapper. Invalid history/overflow produces ERROR; no exception details leak. Coherent snapshots avoid the Data API row cap. A 100,000-revision calculation bound yields ERROR rather than pretending to know a truncated balance. Large-history pagination is deferred until a complete-history protocol is designed.
