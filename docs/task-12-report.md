## Financial policy and compatibility

Algorithm v1 requires at least three current posted monthly occurrences and preserves household/account, normalized literal description, explicit merchant identity where available, currency and allocation ownership. Single negative EXPENSE allocations qualify for automatic hypotheses; other effects/openings/states, positive refunds and known card settlement payment/counterpart evidence are excluded explicitly. Mixed loan principal/interest/fee transactions are not automatic candidates; a negative expense allocation can be reviewed explicitly without treating principal as expense. Exact amounts, consecutive months and a uniquely compatible clamped day provide supporting evidence. Variable amounts, multiple movements in a month, missing months or irregular/ambiguous days remain ambiguous. Identical text cannot certify merchant/contract identity; missing external coverage always stays visible. Account metadata edits do not resurrect unchanged accepted/rejected evidence.

Confirmed plans retain original positive exact Money, account/currency/ownership and originating evidence. Supported scope is monthly EXPENSE planning only. Short months clamp days 29–31 to their last valid day, using the existing portable Gregorian primitive; February/leap years and December 9999 are supported without timezone or holiday adjustments. Start/end dates are inclusive. Version windows begin inclusively at explicit effectiveFrom and end exclusively at the next version's effectiveFrom; earlier windows and decisions remain retained. Edits require a strictly later effective date and cannot silently orphan active payment links. Ended plans can be archived later without inventing new events. Computation is bounded to 120 calendar months and 1,000 expected dates.

Actual linking requires explicit acknowledgement of a current posted negative EXPENSE allocation, matching household/account/currency/ownership and exact revision identities. One transaction can be claimed by one occurrence; the occurrence has one active link. Equal amounts become ASSOCIATED only after confirmation; smaller/excess amounts remain PARTIAL/AMBIGUOUS. Correction/void makes retained evidence STALE, requiring explicit unlink/new review. Unlinked remains UNRESOLVED, never automatically missed. Receipts recover the original command outcome while fresh snapshots independently evaluate current validity. There is no cross-currency FX matching, future rate or combining multiple partial payments. Currency display uses existing minor-unit formatting; all stored and compared amounts retain eight-place precision.

Existing canonical contracts are unchanged. Two exact ES-only aliases are added consistently to architecture, TypeScript and Deno configuration. The existing reporting context validator is reused without changing financial formulas. One bounded STABLE invoker snapshot nests reporting and complete planning histories under one RLS/MVCC statement. Combined limits are 10,000 obligation/rejection/link decisions, 100,000 original reference rows and 16 MiB; overflow returns fixed SafeError, never truncated success. Payment choices render only on explicit review; over 1,000 eligible options blocks that UI operation visibly.

The additive CLI-created `20261013140025_task12_recurring_obligations.sql` introduces nine planning/history/claim/receipt/audit tables, restrictive household/account/member/revision/allocation FKs, household SELECT RLS and no client DML. Private helpers are withheld from clients. The narrow fixed-search-path command locks household then Auth user/session/member and account, reauthorizes before complete-payload SHA-256 receipt replay, checks expected versions and current financial evidence, and commits decisions/claims/minimal audit atomically. Original allocation evidence can justify only one candidate-origin confirmation, preventing concurrent duplicate approvals with different IDs. No new dependencies or financial writer are introduced; finance/private remain unexposed.

## Limits and handoff

External statement coverage and merchant/contract identity are not certified. Imported canonical provenance references are retained, but no source-specific merchant inference or provider adapter is added. Monthly expense-only planning, same-account/same-currency actual matching, one whole transaction per occurrence and immutable account/currency/ownership constrain this release. Principal, transfers, investment obligations, cross-currency payment matching, combinations of partial payments, weekly/annual schedules and business-day shifts are unsupported. Manual plans can intentionally coexist; names/amounts never prove duplicate contracts. Financial revisions changing the reviewed reference set can require review against existing plans. Current corrected knowledge is used, not a frozen recorded-time report.

Browser command memory is lost on reload/unmount; users must inspect durable history before starting a new decision after an uncertain outcome. Large/invalid graphs and oversized choice lists fail visibly; scaling needs a reviewed retrieval/interaction protocol. Chromium desktop/mobile emulation is covered; other engines/physical devices are not claimed.
